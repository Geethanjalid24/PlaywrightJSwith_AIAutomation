# OrangeHRM AI-Driven E2E Automation Framework

Playwright + JavaScript automation framework built for the **Quality Engineer (Automation) — AI Test Engineer** technical assessment. It automates the full **Employee Lifecycle Management** scenario against the [OrangeHRM demo site](https://opensource-demo.orangehrmlive.com/), with Page Object Model, self-healing locators, screenshot (visual) comparison, API cross-validation, video evidence, and an MCP configuration that lets an AI agent (e.g. Claude) drive, inspect, and help maintain the suite.

> **AI disclosure:** This framework — folder structure, Page Objects, self-healing locator engine, screenshot-comparison harness, custom timing reporter, MCP configuration, and this README — was generated by an AI test engineer (Claude) from the assessment's job description and instructions, then organized for human review and hand-editing. Locators are written against the real OrangeHRM demo DOM structure as of this writing; run the suite once to confirm, since the AI did not have live execution access while authoring the selectors. See [`AI.md`](./AI.md) for the full AI-generation and design-decision log.

## 1. What This Automates

**Scenario: Employee Lifecycle Management**

| Step | Action | Validation |
|---|---|---|
| 1. Login | Log in with valid credentials | Dashboard visible, URL check, visual checkpoint |
| 2. Add Employee | PIM → Add Employee, data-driven from `test-data/employee.json` (first/last name, Employee Id, profile picture upload) | Personal Details page loads (success), visual checkpoint |
| 3. Edit Employee | Search by Employee Id, update Job Title + Employment Status | Field values reflect the update, visual checkpoint |
| 4. API Validation | Create/update/verify a record at the API layer, cross-check field values against what was set in the UI | Status codes + field-by-field cross-check assertions |
| 5. Delete Employee | Delete via UI | "No Records Found" in UI search, API delete confirmed |
| 6. Logout | Log out | Redirected to login, protected route blocked post-logout |

Every step is wrapped in a named `test.step()` (visible in the HTML report), and every major validation captures a screenshot — either compared against a baseline (visual regression) or stored as timestamped evidence.

## 2. Framework Architecture

```
orangehrm-ai-automation/
├── mcp.config.json              # Playwright MCP server config (AI agent tooling — see §7)
├── playwright.config.js         # Test runner config: video=on, HTML report, custom timing reporter
├── package.json
├── .env.example                 # Copy to .env for local overrides (base URL, creds, API url)
├── test-data/
│   ├── employee.json            # Data-driven input: credentials, new employee, edit values, API config
│   └── assets/
│       └── profile-picture.png  # Sample upload file used in Add Employee step
├── pages/                       # Page Object Model
│   ├── BasePage.js              # Shared self-healing locator + screenshot + step-wrapper helpers
│   ├── LoginPage.js
│   ├── DashboardPage.js
│   ├── PimAddEmployeePage.js
│   ├── EmployeeListPage.js
│   └── EmployeeJobDetailsPage.js
├── utils/
│   ├── SelfHealingLocator.js    # Core self-healing locator engine (§5)
│   ├── ScreenshotHelper.js      # Visual regression + evidence capture (§6)
│   ├── ApiHelper.js             # API validation + UI/API cross-check helper
│   ├── Logger.js                # test.step() wrapper + console logging
│   └── TimingReporter.js        # Custom Playwright reporter: total + per-test execution time
├── tests/
│   └── employeeLifecycle.spec.js  # The end-to-end scenario, step by step
├── reports/                     # Generated at run time (git-ignored except baselines) — see §4
│   ├── html-report/             # Playwright HTML report (video + screenshots embedded)
│   ├── screenshots/             # Durable per-step evidence PNGs
│   ├── self-healing/healing-log.json  # Locator healing events
│   └── results/                 # JSON results + execution-time.json
└── .github/workflows/playwright.yml   # CI pipeline that runs the suite and uploads artifacts
```

**Design principles**

- **Page Object Model** — one class per screen/module; tests read like a script of business actions, not raw selectors.
- **Data-driven** — all test inputs live in `test-data/employee.json`; swap in a CSV/JSON loader per environment without touching test logic.
- **Descriptive assertions** — every `expect()` includes a message stating what should be true and why (see any `pages/*.js` file).
- **Resilience over brittleness** — locators are arrays of fallback strategies, not single selectors (§5).
- **Evidence-first reporting** — video, screenshots, and timing are non-optional parts of every run, not opt-in extras (§4).

## 3. Setup Instructions

### Prerequisites
- Node.js 18+ (Node 20 recommended)
- Git

### Install

```bash
git clone <this-repo-url>
cd orangehrm-ai-automation
npm install
npx playwright install --with-deps chromium
cp .env.example .env   # optional — defaults already point at the public demo site
```

### Run the tests

```bash
npm test                    # headless run (default)
npm run test:headed         # see the browser
npm run test:ui             # Playwright's interactive UI mode — great for debugging locators
npm run test:debug          # step-through debugger
```

### View the HTML report (with embedded video + screenshots)

```bash
npm run report
```
This opens `reports/html-report/index.html` in a browser. Click into the test → each `test.step()` is listed with its own duration; failed steps show the attached failure screenshot; the **Attachments** panel has the full test video and every visual checkpoint.

### Update visual baselines (first run, or after an intentional UI change)

```bash
npm run test:update-snapshots
```
Baseline PNGs are written to `tests/__screenshots__/` — **commit these** so future runs have something to diff against. (First-time run auto-creates them if missing.)

### Total execution time

Printed to the console at the end of every run, and persisted machine-readably at `reports/results/execution-time.json`:

```
========================================
 EXECUTION TIME SUMMARY
========================================
  [PASSED] Employee Lifecycle Management @e2e > Login → Add → Edit → API Validate → Delete → Logout — 42.17s
----------------------------------------
  TOTAL EXECUTION TIME: 42.17s
========================================
```

## 4. Reporting & Evidence

| Requirement | Where it's satisfied |
|---|---|
| HTML test report | `reports/html-report/` (Playwright's built-in reporter — `playwright.config.js` → `reporter: [['html', ...]]`) |
| Video evidence | `video: { mode: 'on' }` in `playwright.config.js` — every run, pass or fail, attached to the HTML report and saved under `reports/test-artifacts/**/video.webm` |
| Failure screenshots | Automatic on any assertion/action failure (`screenshot: { mode: 'only-on-failure' }`) **plus** an explicit `captureFailure()` call in `BasePage.runStep()`'s catch block, so a failure inside any step is always evidenced even if Playwright's automatic capture races the teardown |
| Per-checkpoint screenshots | `ScreenshotHelper.compare()` / `.capture()`, called after each of the 6 scenario steps — see `tests/employeeLifecycle.spec.js` |
| Total execution time | Custom `utils/TimingReporter.js`, registered in `playwright.config.js`, prints a summary and writes `reports/results/execution-time.json` |
| Machine-readable results | `reports/results/results.json` (Playwright's `json` reporter) |
| Self-healing activity | `reports/self-healing/healing-log.json` — every time a fallback locator strategy had to be used |

## 5. Self-Healing Locators

Traditional Playwright locators are single, fixed selectors — if the DOM changes, the test fails. This framework instead defines every element as an **ordered list of independent locator strategies**, implemented in [`utils/SelfHealingLocator.js`](./utils/SelfHealingLocator.js):

```js
this.usernameInput = this.locator('Login > Username Input', [
  p => p.getByPlaceholder('Username'),        // strategy 0 (primary) — semantic, most readable
  p => p.locator('input[name="username"]'),   // strategy 1 (fallback) — attribute-based
  p => p.locator('.oxd-input').first(),        // strategy 2 (fallback) — structural, last resort
]);
```

At execution time, `resolve()`:
1. Tries strategy 0. If it attaches within the timeout, use it — no healing needed.
2. If strategy 0 fails, tries strategy 1, then strategy 2, etc.
3. The **first strategy that finds the element wins**. If that was *not* strategy 0, a **healing event** is logged to `reports/self-healing/healing-log.json` (element name, which strategy healed it, why the earlier ones failed, current URL, timestamp) and a warning is printed — the test **keeps running instead of failing**.
4. Only if **every** strategy fails does the framework throw, with a clear message listing what was tried.

This means: a class name renaming, an attribute reshuffle, or a structural DOM change does **not** break the suite as long as one of the declared fallback strategies still resolves the element — and the healing log tells a human (or an AI reviewing the repo) exactly which locators are getting brittle and should be promoted/fixed.

`SelfHealingLocator` also exposes convenience methods (`.click()`, `.fill()`, `.selectOption()`, `.textContent()`, `.isVisible()`) so Page Objects stay concise.

## 6. Screenshot Comparison (Visual Regression)

`utils/ScreenshotHelper.js` wraps Playwright's native `expect(page).toHaveScreenshot()`:

- `compare(checkpointName)` — full-page screenshot, pixel-diffed against a committed baseline in `tests/__screenshots__/`, threshold set in `playwright.config.js` (`maxDiffPixelRatio: 0.02`). On mismatch, Playwright attaches actual/expected/diff images to the HTML report, and the framework also copies the checkpoint into `reports/screenshots/` as durable evidence.
- `capture(label)` — plain evidence screenshot (no baseline diffing) for steps where pixel-exact comparison isn't meaningful (e.g. a page containing a live-generated numeric ID).
- `captureFailure(stepName, error)` — invoked automatically from `BasePage.runStep()` whenever any step throws, guaranteeing a screenshot exists for every failure regardless of which line failed.

Checkpoints in this suite: dashboard-after-login, employee-form-filled, employee-created (with the dynamic system ID masked out of the diff), search-results-found, job-details-updated, and employee-deleted.

## 7. MCP Configuration (AI Test Engineer Tooling)

[`mcp.config.json`](./mcp.config.json) configures the [Playwright MCP server](https://github.com/microsoft/playwright-mcp), which exposes a real, controllable browser to any MCP-compatible AI client (Claude Desktop/Code, etc.) as a set of tools: navigate, click, type, snapshot the accessibility tree, take screenshots, and so on.

**Why this matters for an AI Test Engineer role:** it lets an AI agent *interactively* drive the live OrangeHRM site — inspecting real DOM/ARIA structure, verifying a candidate locator actually resolves, or diagnosing why a self-healing event fired — rather than guessing selectors from static analysis alone. In this repo it's used for:

- **Locator authoring & verification** — before committing a `SelfHealingLocator` strategy list, drive the real page via MCP to confirm each fallback strategy actually matches.
- **Debugging healing events** — when `reports/self-healing/healing-log.json` shows a strategy failing, an AI agent can reconnect via MCP, load the same URL, and propose an updated/new fallback strategy.
- **Exploratory maintenance** — after an OrangeHRM demo-site update, re-walk the flow via MCP to spot broken steps before the scheduled CI run does.

Start the MCP server standalone:

```bash
npm run mcp:server
```

Then point your MCP client (e.g. Claude Desktop's `claude_desktop_config.json`, or Claude Code's MCP settings) at it, e.g.:

```json
{
  "mcpServers": {
    "playwright-orangehrm": {
      "command": "npx",
      "args": ["@playwright/mcp@latest", "--config", "mcp.config.json"]
    }
  }
}
```

Key settings in `mcp.config.json`:
- `browser.launchOptions.headless: false` — AI-driven sessions run headed so a human can watch/intervene.
- `network.allowedOrigins` — locked to the OrangeHRM demo host and the ReqRes API host, preventing the agent from wandering off-scope.
- `saveTrace` / `saveSession: true` — every MCP-driven session is recorded for later review, under `reports/mcp-session-artifacts/`.

## 8. API Validation Strategy

The assessment step "Validate Employee via API" asks to use the OrangeHRM API, **or** simulate it with a public test API (ReqRes) if unavailable. The OrangeHRM demo instance does not expose a stable, unauthenticated REST endpoint for PIM employee CRUD, so this framework uses **[ReqRes](https://reqres.in)** to simulate the API layer, while the UI steps run against the real OrangeHRM record:

1. After the UI creates/edits the employee, `utils/ApiHelper.js` calls ReqRes (`POST/PUT/GET/DELETE /users`) with the **same field values captured from the UI** (Employee Id, Job Title, Employment Status).
2. `ApiHelper.crossCheck(uiValues, apiPayload, fieldMap)` performs a real field-by-field comparison and returns a structured mismatch report, which the test asserts on with a descriptive message.
3. Delete is verified two ways: UI search returns "No Records Found", **and** the simulated API delete call returns `200`/`204`.

**To point this at a real API** (a real OrangeHRM instance with API access, or an internal service), only `utils/ApiHelper.js` and `test-data/employee.json` → `api.baseUrl` need to change — no test or Page Object code is affected, since the cross-check contract (`fieldMap`) is provider-agnostic.

## 11. Extending the Framework

- **New scenario**: add a `tests/<name>.spec.js`, reuse existing Page Objects or add new ones under `pages/`.
- **New data set**: add another JSON/CSV under `test-data/` and `require()`/parse it in the spec — no framework changes needed.
- **New self-healing element**: call `this.locator('Descriptive Name', [strategy0, strategy1, ...])` inside any Page Object constructor.
- **New visual checkpoint**: call `pageObject.screenshots.compare('checkpoint-name')` after any state change worth diffing.
